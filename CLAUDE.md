# CoachBuild — technical reference

**Describes v0.92.1, 2026-08-01.** `package.json`'s `version` is the single source of truth for the app version — if it's moved on since this date, treat anything below with more skepticism the further it's fallen behind (check `CHANGELOG.md` for what shipped after this doc's version).

League of Legends coaching companion. Next.js 16.3 (App Router) + TypeScript + Tailwind, Vercel (prod: `coachbuild.vercel.app`, personal account). Serverless throughout — no server processes besides Vercel functions + three daily crons, plus a user-run PowerShell companion (`public/companion.ps1`) that bridges the app to the local League client. `NEXT_PUBLIC_APP_VERSION` is injected by `next.config.mjs` from `package.json` and shown in the global nav's rail/tab-bar footer; the SW cache name is version-tied. Read this file before exploring source; it's the map, not a substitute for reading the actual code before changing it.

## Six surfaces, one shell

Every route renders inside `AppShell.tsx` (`app/layout.tsx`, wraps `CompanionProvider`) — a global gold/navy `TopBar` (champion search + live champ-select chip + APPLY RUNES button, `components/hextech/GlobalNav/TopBar.tsx`) plus `DesktopRail` (`≥lg`, branded left rail, PLAY group: Builds/Draft/Companion; DATA group: Pro Players/Patch Movers/My Stats; live companion status card; `PATCH n · vX.Y.Z` footer) or `MobileTabBar` (`<lg`, fixed bottom, **FIVE cells**: four fixed bar destinations Builds/Pro Players/Patch Movers/My Stats plus a **More** button that opens a bottom-sheet `role="dialog"` exposing the remaining three — Draft, Post-Game, Companion (`MOBILE_OVERFLOW_NAV_ITEMS`, the exact complement of `MOBILE_NAV_ITEMS`). **Corrected 2026-08-12:** the bar was 4-destination-only until 2026-08-10, when the `mobile` flag was redefined so `mobile: false` now means "reached through the More sheet", NOT "unreachable on a phone" — `/draft` and `/live-setup` render and operate fine on mobile. Nav data source: `components/hextech/GlobalNav/navItems.ts` (`NAV_ITEMS`, `MOBILE_NAV_ITEMS` derived via a `mobile` flag) + `activeNav.ts`. Champion search is global now (`championSearchBus.ts` — a pub/sub the Builds page subscribes to; searching from any route navigates to `/` and selects the champion).

**Builds (`/`, `app/page.tsx`)** — pick a champion, get the WPA-ranked (Win Probability Added) recommended runes/shards/items/spells, sourced live from coachless.gg's deep-learning stats API (`lib/coachless.ts`, a thin proxy — no key/auth, public endpoint). `lib/recommend.ts` ("THE ENGINE") evaluates every primary tree and every secondary tree and returns up to 3 confidence-weighted variants (`buildRecommendations`). Route: `app/api/build/route.ts` → 200 with `BuildResponse[]`, 404 (`error: "Champion not played in this role"`) when the champ+role lacks data (`NotPlayedInRoleError`), 500 with no detail leak on genuine failure. The champion param is `champ`, not `championId`. Optional params: `rank=<bracketId>` (`lib/rankBrackets.ts`, default `all` = legacy High-Elo blend `[5,6,7]`) and `enemyChampionId=<int>` (matchup conditioning — confirmed 403 on every coachless endpoint, `BuildResponse.matchup.supported` always `false`; wired but dormant). v0.51.0 unified the page into one view: lane tabs (TOP/JG/MID/BOT/SUP) live inside `ChampionHero`; a HIGH/MEDIUM/LOW CONFIDENCE chip (`confidence.ts`, games-count banding) replaces the old separate BUILD/PRO BUILDS tab strip. **Corrected 2026-08-12:** the elo PILL ROW (its old `HERO_ELO_OPTIONS` list, whose "Diamond" pill wrongly sent tier `[5]` = Emerald) was **REMOVED 2026-08-11**. There is exactly ONE bracket now, `DIAMOND_PLUS_BRACKET`, rendered as static "All data from Diamond+" scope copy in the slot the pills used to occupy — no elo/rank selector exists at any width (was ~v0.107.0's single `diamond-plus` bracket, pills fully gone by v0.109.0). Pro browsing (the old "PROS mode") moved to `/history`. v0.70.0 added a THIRD consensus surface below the build: the mobile tab strip is now **BUILD | PRO | OTP**, and `ProConsensusCard.tsx` renders both consensus cards via a `variant` prop (`"pro"` → `/api/pros`, `"otp"` → `/api/otp`). One component on purpose — HARD RULE 2's starter partition and the per-slot honest denominators are then enforced in exactly one place. Both variants render the companion apply buttons (v0.70.1). Icon/data CDN URLs and "what patch is live" resolution live in `lib/staticData.ts` — see Gotchas.

**Draft (`/draft`, `app/draft/page.tsx`)** — **REDESIGNED to the "Draft Assistant" layout in v0.90.0** (two columns: role/pick/ally/enemy control row, three derived TOP RECOMMENDATIONS cards, a Recommended/Blind Picks/Counters/Comfort Picks tab strip, a real filter row, a legend, WORST MATCHUPS PREVIEW, and a DETAILED RANKINGS panel with Off-Meta tags). Hero cards draw from META champions only (user directive: an off-meta one-trick must not be the first thing you see); the tables still show off-meta rows, tagged. **That asymmetry is a trap and cost two rounds in v0.93.0** — the cards prefer meta (`chooseSlot` in `components/hextech/draftAssistantModel.ts` exhausts non-off-meta candidates in every source group first) while DETAILED RANKINGS sorts purely by value, so at the DEFAULT 0% Min. Pick Rate a wall of 0.2%-pick-rate champions outranked the champions the cards were recommending. Two invariants now hold and are test-pinned: with **no enemies picked** the Recommended view merges the filtered BLIND rows (dedup by champId, filters authoritative, matchup rows ahead of blind on ties) and says so in the panel — the matchup-driven feed is near-empty pre-enemy, which is why the table used to show a single row against three cards; and **every champion on a hero card is guaranteed to appear in the rankings**, appended under "CARDED RECOMMENDATIONS · SHOWN FOR REFERENCE" at its TRUE rank and values when it falls outside the visible window. The honest sort is never reordered, nothing is pinned upward, and a card excluded by an active filter stays excluded. `fullLaneCandidates` remains a per-slot card fallback and is deliberately NOT merged into the table (that would duplicate "View full table"). Comfort Picks is a PURE FILTER over the existing order and never re-scores (hard rule 3). Team synergy and a My-Stats weighting control were both deliberately CUT. **Ban suggestions are ARCHIVED, not deleted** — still computed by the API, unreachable in the UI, with the full revival note and the ban formula in `docs/archive/draft-bans/README.md`; that file also lists the ten now-dormant components.

Underneath the redesign the engine is unchanged: it suggests statistically-favored picks for a lane given the enemies entered (manual picker or auto-filled live via the companion). Sourced from u.gg's stats2 CDN (`lib/draft/ugg.ts`), one tier — **`DIAMOND_2_PLUS_TIER = 15`, Diamond II and above** (v0.108.0; the old `EMERALD_TIER = 10` was a guessed name that was wrong, tier 10 is u.gg's `PLATINUM_PLUS`, so `/draft` served Platinum+ for months while Builds served Diamond+ — see `wiki/gotchas.md` for the confirmed enum and the arithmetic that checks it) — ingested into `coachbuild.draft_matchup`/`draft_champ_stats` and scored with a shrinkage-toward-baseline model (`lib/draft/score.ts`: `n/(n+K)`, K=200, floor 30 games; direct-lane-opponent weight 1.0x vs off-lane 0.2x; bans rank by disadvantage × presence, excluded entirely below `BAN_MIN_MATCHUP_GAMES=1000`). v0.51.0 retheme: shared navy/gold shell (cyan HUD retired); ENEMY COMP PROFILE renders as horizontal 0–100 bars (`DraftCompBars.tsx` over the curated 173-champion `lib/draft/compRatings.ts` ratings, replacing the old radar) plus up to 3 tactical takeaway chips (`lib/draft/compTakeaways.ts`, editorial thresholds — honest fallback text like "High ban priority" when a specific claim isn't backed by data, never an invented mechanic like "denies your sustain"). (Pre-v0.90.0 layout notes — the 2-col shell, inline ban suggestions in `MyChampionPanel`, and `DraftCompBars` — describe the RETIRED page; see the redesign note above and `docs/archive/draft-bans/README.md`.) `personal`/`personalOverall` per-row badges (My Stats integration, display-only — see hard rules). `GET /api/draft/recommend`'s `meta.fetchedAt` (v0.87.0) is `MAX(ingested_at)` over the rows actually served, not serve-time `new Date()` — the freshness label now shows real data age. The page also surfaces `meta.ingestHealthy === false` as a one-line notice (read via `getIngestHealth`, soft-failed to `null`/no notice on read error — never a fabricated "healthy") — see `lib/ingestHealth.ts` below. **Champion ids in the 60000+ range are ALTERNATE-ART entries, not champions, and must be filtered out before any u.gg request (v0.95.0).** From 2026-07-30 to 2026-08-03 the ingest asked u.gg for 60001/60002/60004, got a Cloudflare challenge because there is nothing to serve, and flipped `ingestHealthy` false for four days over champions that do not exist. The filter lives in BOTH `lib/draft/ingest.ts` and the production `scripts/ingest-draft.mjs` — a real roster is 173, not 176. The honest fix for a bot challenge is to stop making the request, never to evade the protection. Note also that plain Node `fetch` is Cloudflare-challenged from a dev machine even for a valid champion; the scheduled script's transport is the working path, so a local `fetch` probe failing proves nothing about production.

**Companion (`/live-setup`, `app/live-setup/page.tsx`)** — install/pairing UI for the PowerShell tray companion. `components/hextech/companion/StatusHeroCard.tsx` shows a 4-step Client→Lobby→Champ Select→In Game progress rail; `AutomationToggles.tsx` are real `role="switch"` controls (auto-apply runes / auto-apply item sets) with a privacy footnote. Its copy now states the real item-set contract — one set per champion+role with WPA / Pro / OTP / Hidden gem blocks plus Starting (v0.87.0 fix; the copy previously described a removed "up to 3 item sets" shape from before v0.71.0 — see "Companion integration" below for the actual current contract). Connection-test/LNA explainer/rolling error-log machinery (`recordCompanionError`, last 5 shown) sits below the fold. See "Companion integration" below for the LCU bridge contract.

**My Stats (`/mystats`, `app/mystats/page.tsx`)** — personal match tracker for MULTIPLE linked Riot accounts (v0.83.0; `MY_RIOT_ID`/`MY_RIOT_REGION` is now only the seed/fallback, not the identity). Accounts are detected from the League client and persisted; the account picker switches between them and **every figure is scoped to the displayed account** — `lib/mystats/account.ts`, `components/hextech/mystats/AccountPicker.tsx`. Two invariants pinned by structural tests, both learned the hard way: **(1) the LCU's `puuid` is a 36-char local UUID, NOT Riot's 78-char encrypted PUUID** — always re-resolve identity from `gameName`+`tagLine` through account-v1 (v0.83.1). **(2) only ranked solo/duo (queue 420) counts** — `lib/mystats/queues.ts`'s `COUNTED_QUEUE_IDS`, bound by SEVEN reads including `lib/draft/recommend.ts`'s personal badges; the ingest deliberately stores every queue and the filter lives at READ time, so a new read that forgets it silently counts flex (v0.86.0, `mystats-queue-invariant.test.ts` fails such a read by construction). Backfilled from Riot match-v5 into `coachbuild.my_matches` (`lib/mystats/**`). The TrackDIFF-shaped profile UI (v0.84.0–v0.86.0: hero band, account card grid, Champion/Match Performance panels) was retired by a later page rewrite and its 10 orphaned components were DELETED in v0.110.2 (user-approved; see `wiki/decisions.md`). `components/hextech/mystats/` now contains ONLY the live `AccountPicker.tsx` + `accountPickerModel.ts`; everything else on `/mystats` (stat tiles, champion pool, recent games) is composed inline in `app/mystats/page.tsx`. Two v0.110.1 UI conventions bind here: missing data never renders as a dash with a unit welded on (formatters return `—` for null; call sites branch instead of appending units), and `StatTile` bars are opt-in nullable — only rendered when they encode a real ratio, with `role="img"` + aria-label. `MyStatsRefresher.tsx` fires an on-demand incremental refresh (`POST /api/mystats/refresh`, 3-min server-side cooldown, `lib/mystats/refresh.ts`) on every page view. **DISPLAY-ONLY, hard rule** — see below. **Scoped to the CURRENT SEASON, and to nothing narrower — splits are NOT a display scope (hard user directive, 2026-08-01: "Don't separate games into splits. I just want all games from the same season counted together").** v0.88.0 removed split filtering from every read in `app/api/mystats/summary/route.ts`, deleted `priorSplitWinrate` and `currentSplitNumber`/`priorSplitStartMs`, and pinned `lib/mystats/purge.ts`'s DELETE cutoff to `SEASON_START_MS`. This was a real user-visible bug, not a preference: an account that played Jan–Apr, stopped, then played 2 games in July saw "2 games" under every panel while the account card above it said "142g · 60.6%" — and `/draft`'s personal badges (never split-scoped) disagreed with `/mystats` on the same data. The split COLUMN survives and `lib/mystats/extract.ts` still tags every row via `splitForGameCreation`; it is storage metadata with no reader. `mystats-queue-invariant.test.ts` now asserts structurally that no `my_matches` statement contains a `split =` predicate, so re-adding one fails the suite. Every heading/label says "this season" (or "recorded so far"/"so far this season" when `coverage.seasonClaimSafe` is false) via the single `getMyStatsScopeLabels` helper in `components/hextech/myStats.ts` — take scope wording from there, never a fresh string. adherence/KDA/items/keystone only populate for matches ingested/backfilled after migration 0014 landed AND only resolve `on_wpa_build` when the match's own patch matches the live recommend pipeline's current patch (no historical-patch override exists) — a match on an older patch shows no adherence chip. Since v0.87.0, that null case is no longer one undifferentiated "not recorded": `lib/mystats/adherence.ts`'s `comparePatchLabels`/`isWaitingForPatchData` distinguish genuine upstream lag (the match's patch is NEWER than the patch coachless has actually populated → "waiting for patch data") from a genuinely unresolved build (→ "build not recorded"); the underlying gate itself is unchanged, this is a read-time classification of an already-null value.

**Patch Movers (`/movers`, `app/movers/page.tsx`)** — v0.51.0 semantic rewrite: per-CHAMPION win-rate shifts (was per-keystone/item WPA swings). `lib/patchMovers.ts` unions a curated per-role candidate pool (`ROLE_CHAMPION_POOL` — coachless has no champion-list/tier-list endpoint, so this is NOT a true ladder top-N) across all 5 lanes, computes win rate via the same occurrence-weighted starter-item formula `lib/heroStats.ts` uses for the hero banner, diffs current vs. previous populated patch, sorts by `|Δpp|`, applies a min-games floor. Single table, no lane pills. Curated one-line patch notes (`lib/patchNotes/`, web-verified per-patch entries only — absent shows "—", never fabricated).

**Pro Players (`/history`, `app/history/page.tsx`)** — search a tracked pro player or a champion, see recent games; player/champion search-first is the page's primary (and, since v0.51.2, only) view — a recent-competitive-games table was added in v0.51.0 and removed in v0.51.2 per user directive (files deleted, do not resurrect without asking). Two independent data sources feeding one unified response shape:
- **Solo queue** — `lib/pro/**`. Roster from lolpros.gg, matches from Riot match-v5 + timeline, stored in `coachbuild.pro_matches`/`pro_accounts`/`pros`.
- **Pro play (on-stage)** — `lib/prostage/**`. Official esports games from Leaguepedia (lol.fandom.com Cargo tables), stored in `coachbuild.prostage_matches`. Item build order reconstructed on first view from lolesports' free livestats feed and persisted.

A THIRD roster exists as of v0.70.0 but is deliberately **not** part of this page: **OTPs (one-tricks)** — `lib/otp/**`, discovered from op.gg's champion leaderboard, stored in `coachbuild.otp_accounts`/`otp_matches`, served by `GET /api/otp` and consumed only by the Builds page's OTP Consensus card. They are ladder players, not pros; keeping them out of `pros`/`pro_accounts` is what stops every "pro" surface in the app quietly becoming a lie (same reasoning migration 0012 used for `my_account`).

Both merged by `app/api/pros/route.ts` (`GET /api/pros`) into one `ProGame[]`. `GET /api/players?q=` is player typeahead. `GET /api/prostage/timeline?player=...` computes/serves a pro-play game's item build order on demand. `GET /api/pros/team-players` fetches one game's full per-player team builds on demand when a detail sheet opens.

Vercel crons (`vercel.json`): `/api/ingest/matches` 06:00 UTC **every 2 days** (`0 6 */2 * *` — not daily; the real solo-queue sweep is the local `CoachBuildMatchIngest` scheduled task, and `/api/pros/refresh` covers on-demand freshness), `/api/ingest/prostage` 07:00 UTC (one tournament/invocation, staleness-rotated), `/api/ingest/mystats` 20:00 UTC (daily — the Vercel free plan caps cron frequency at once/day; on-demand incremental refresh via the page-view trigger covers the gap between runs). `/api/ingest/draft` runs on a separate schedule for the u.gg matchup refresh.

## Companion integration (LCU bridge)

`public/companion.ps1` — a PowerShell 5.1 tray app, installed via `irm https://coachbuild.vercel.app/companion.ps1 | iex -Install`, versioned independently of the web app (check `public/companion.version` or the `Version =` literal near the top of `companion.ps1` for what's actually served — this doc's own version number rots fast, and served-vs-doc drifted before; served over `irm|iex` so users must re-run the install one-liner to pick up a bump — check each CHANGELOG entry's "(COMPANION CHANGE → x.y.z — re-install required)" tag). - **Champ-select follow.** `followKindForRoute(pathname)`: `"/"` → `"builds"`, `"/draft"` → `"draft"`. The `/status` poll sends `&follow=builds|draft`; the companion opens whichever page(s) are missing an attached tab (neither attached → Builds then `/draft`; one attached → only the other; both → no opens). **Suppression invariant:** an attached tab (a follow poll inside `AttachWindowSeconds`, 150s since v1.6.4 — Chrome throttles a hidden tab to ~1 tick/min behind a fullscreen game) suppresses re-opening a new browser tab on every champ-select hover — load-bearing UX, don't regress it into "always open a new tab."
- **Opening is ENTRY-triggered, and "attached" needs live proof (companion 1.7.0, v0.59.0).** Both pages are opened on champ-select ENTRY (`Invoke-ChampSelectPrewarm`) — Builds via a session-only `/?session=` (no champion has resolved yet; the tab adopts the session in `app/page.tsx`'s mount effect and live-follows the first hover in place), so a cold browser boots during bans instead of mid-pick. The three-way rule for whether a kind counts as attached: an open→attach grace (25s), a follow stamp inside the 150s window, **and** — new — the stamp is only trusted while a browser process exists (`Test-BrowserProcessRunning`) and until the page says otherwise. `detachFollow` (`CompanionProvider`) fires `follow=<kind>&detach=1` on `pagehide` and when a client nav leaves a follow-capable route; the bridge clears that kind's stamp and records `LastXDetachAt`, which also voids a grace it postdates. **Never wire detach to `visibilitychange`** — a hidden tab is the normal state here and is still following; detaching on hide re-creates the v1.6.4 tab-spam bug.
- **Auto-export.** `components/live/AutoExporter.tsx` (mounted once in `CompanionProvider`, app-wide, every route) reacts to champ-select champion resolution and pushes item sets + runes through the same apply pipelines the manual buttons use, deduped per `(championId, laneId)`. - **Item sets — the whole-document PUT is the constraint, NOT a 4KB budget.** This line used to claim a "4KB LCU per-object budget"; that figure appears nowhere in `companion.ps1`, its `-SelfTest`, or the CHANGELOG, and a real capture (2026-07-27, `scripts/capture-lcu.ps1`) **disproves it**: the live item-set document on a real account measured **61,060 bytes across 62 sets** and reads/writes fine. Design to the MECHANISM, which is fully scar-backed: the PUT replaces the entire document, so an oversize payload is rejected ALL-OR-NOTHING (HTTP 413 in v0.46.0 — none of the CoachBuild sets landed, not just the excess). The prune is what bounds our contribution at O(1); the danger is unbounded growth, not a specific byte ceiling. **That capture also raises the stakes on `Merge-ItemSets`: those 62 sets were ALL the user's own, so a merge bug is 61KB of someone's data, not a rebuildable cache.** **EXACTLY ONE set per champion+role.** Title/uid are `CoachBuild <champ> <role>` / `coachbuild-<champ>-<role>`, byte-identical to every version that has shipped, so an existing install is replaced in place. **v0.112.0 briefly (32 minutes) emitted a SECOND `CoachBuild <champ> <role> Situational` set; v0.113.0 removed it** — the user saw both in the shop's set dropdown and rejected it ("you added it as a new set i just wanted it in the same default set from coachbuild"). The second field is the OPTIONAL overlay delta array (see the Situational paragraph below); it rides on the same return rather than living in its own exported function so that it is derived from the SAME `situationalBlockPicks` call the `Situational` block is built from. Every test call site narrows with a local `(...args) => buildItemSets(...args).sets` shim.

**v0.71.0 — exactly FOUR build blocks, each named for its SOURCE: WPA build / Pro build / OTP build / Hidden gem**, plus the Starting slot (HARD RULE 2 keeps starters out of every completed-item list) and, since v0.112.0, a **Situational** row LAST. **v0.113.0 made that row one block PER ITEM, titled `Situational <delta>` (`Situational +4.27`); v0.114.0 REVERTED it to ONE plain `Situational` block.** The reasoning for the split was sound — an LCU block item is `{id, count}` and a block title is the only writable string anywhere near an item, so a title was the only place a number could go — but the SHAPE was rejected: it took a five-block set to ELEVEN, against a client whose own recommended sets never exceed five ("doesnt look great"). **The numbers now travel on the wire and are drawn by the DESKTOP OVERLAY on top of the item icons.** Concretely: `POST /apply-itemsets` carries an OPTIONAL top-level `situational: {id, wpa, text}[]`, and `situational[i]` annotates the `Situational` block's `items[i]` — same membership, same order, same length. **Both are built from ONE `situationalBlockPicks(items, wpaBuildIds)` call inside `buildItemSets`; do not re-derive the shortlist for the wire.** That is not stylistic: the block applies the WPA-build exclusion, so an independently recomputed wire is a DIFFERENT LENGTH and the overlay paints every number over the wrong icon. A test drives a fixture where the exclusion bites and asserts the pairing index-by-index. `text` is formatted HERE by `wpaText` (the Builds page's own formatter) and the desktop renders it verbatim — a bare `toFixed(2)` would drop the leading `+` off every positive delta; `wpa` is the raw number and the desktop uses only its SIGN, for colour. The field is OMITTED ENTIRELY (key absent, never `[]`, never `null`) when there are no picks. **It is decoration and must never be able to fail an apply**: an older `companion.ps1` hands only `$bodyObj.sets` to `Test-ItemSetsPayload` and never sees the body, and the desktop deserializes `ApplyItemSetsRequest` with `JsonOptions.Wire`, which leaves `UnmappedMemberHandling` at its default of Skip — both pinned by SOURCE assertions in `components/__tests__/situationalItemSet.test.ts`. There is deliberately NO version gate. **Build lines are still not titled with deltas and never were**: they are ordered sequences rather than menus, and Pro/OTP items are ranked on consensus share (`Candidate.raw.scale`), so most carry no WPA at all. How the shop panel renders any of this is still UNVERIFIED (no live game). ## HARD RULES (do not violate without a new explicit user directive)

1. **6-item build-slot cap, but two different shapes for two different things.** A build-line PROGRESSION (Core Order / Buy Order on the Builds page) caps at **5 full items + 1 boots for every lane except Bot/ADC, which gets 6 full items + 1 boots** (the late-game boots-sell exception) — enforced at the single choke point `lib/buildSlotCap.ts`, wired into `lib/recommend.ts`'s `ItemsBlock` assembly. An LCU item-SET export line is a real target loadout and stays capped at **6 total (5 full + 1 boots) for every lane, bot included, no exception** — enforced independently in `itemSetBody.ts`'s `buildLine`. Do not let these two caps drift into each other; they represent genuinely different things (a shopping-order display vs. a real inventory).
2. **Starter-slot partition.** Starting items (Doran's/Cull/Dark Seal/Tear/World Atlas/etc., `STARTING_ITEM_ALLOWLIST`) never render in a completed-item list — they get their own "Starting" slot everywhere a build or Pro Consensus surface exists. Any new aggregate/recommendation surface must carve starters out the same way boots are already carved out.
3. **Display-only personal data never feeds a score or ranking.** My Stats (`personal`/`personalOverall` fields, adherence, KDA, everything under `lib/mystats/**`) is display-only by hard user directive ("Don't mix my data with the sample size," ratified 2026-07-21) — see `lib/draft/recommend.ts`'s `PersonalPlayResult` doc comment. It may badge a row or filter a list (a pure filter, never a re-scorer), but must never alter a WPA/win-rate/priority number or reorder anything beyond what the server's own ranking already produced.
4. **No fabricated data.** Patch notes absent for a given patch render as "—", not an invented note. Ban reasons/matchup claims in Draft's takeaway chips fall back to honest generic language ("High ban priority") rather than a specific mechanic the data doesn't back. A curated/estimated value (compRatings.ts's ddragon-tag fallback, an item-set "(low data)" line) is always labeled as such — never presented as measured.
5. **Companion page/set ownership.** Never delete or overwrite an LCU rune page or item set whose title doesn't start with `"CoachBuild"` — **with one deliberate carve-out: MANUAL rune apply.** A user clicking "Apply runes" gets `Invoke-ApplyRunes`'s `$Mode -ne 'auto'` branch, which does GET currentpage → DELETE → POST regardless of title, because a real click is real consent and a free account with 2 rune slots would otherwise have nowhere to put the page. That behaviour is intentional, documented in `companion.ps1`'s header, and pinned by SelfTest 6c (which asserts the DELETE *does* happen) — do not "fix" it. The rule is absolute for the AUTO path and for item sets, where `Merge-ItemSets` preserves every non-`CoachBuild` set including null/empty-titled ones. Never expand the companion's endpoint surface into anything that acts on the game itself (no auto-pick, no auto-ban, no timer/cooldown computation).

## Hard-won gotchas

**(a) Neon HTTP driver + Next's patched `fetch` — `cache:"no-store"` is load-bearing.** `lib/pro/db.ts`: `neon(url, { fetchOptions: { cache: "no-store" } })`. Never remove — a real P0 (v0.15.1) had stale `{rows:[]}` responses cached across deployments.

**(b) Never CDN-cache an empty API response.** `Cache-Control: no-store` on any empty/degraded result; only non-empty responses earn a long `s-maxage`. Applies to every route serving possibly-sparse data, including the newer `/api/patch-movers` and `/api/patch` routes (audit-verified in v0.51.0).

**(c) Leaguepedia (lol.fandom.com) rate limiting.** `api.php`'s anonymous limit can trip after ONE call and stay sticky 3+ minutes — every caller serialized through one process-wide pacer (`lib/prostage/cargo.ts`, 30s floor). `Special:CargoExport` has a lighter limit (5s floor) but Node's own fetch gets Cloudflare-403'd against it (TLS/JA3-fingerprint block) — script paths shell out to curl instead (`scripts/_curl-transport.mjs`). Never run two concurrent Leaguepedia consumers. Pagination via `offset` now exists on both transports (past the 500-row-per-call cap).

**(cc) SWAPPING WHAT A TAB RENDERS SILENTLY STRIPS EVERY BEHAVIOUR ATTACHED TO THE OLD COMPONENT.** Bit us THREE times on 2026-08-01, all on the OTP tab, which renders `FeaturedOtpCard` where it once rendered `ProConsensusCard`'s `variant="otp"`. Lost, one at a time and each found only by a user: (1) the Apply Runes / Add Item Build buttons (v0.91.0), (2) the `POST /api/otp/refresh` trigger, so no champion ever fetched skill-order timelines — the feature worked for exactly one champion, and only because a script had been run by hand (v0.92.1), (3) the LOW SAMPLE badge, which is why a hero card and the table beside it could name different "best" champions (v0.90.x). **Nothing errors when this happens** — the old component keeps compiling, its tests keep passing, and the capability just stops existing. When you change what a tab renders, enumerate what the outgoing component DID (effects, fetch triggers, buttons, badges) and re-home each one deliberately. Grep for the old component name: if the only hits are comments, its behaviours are orphaned.

**(d) Riot API key budget is shared across every process that calls it.** `lib/pro/pacer.ts` serializes all Riot calls (roster/match ingest, `ingest-player.mjs`, audits, My Stats backfill/refresh) through one process-wide 1.3s-interval queue — but only within a single process. Don't parallelize Riot-calling scripts. The My Stats on-demand refresh endpoint (`/api/mystats/refresh`) is cooldown-gated server-side (3 min) specifically so it's safe to call on every page view without contending for this budget.

**(e) Rune icon special cases.** Deathfire Touch (`8992`) and Stormraider's Surge (`8230`) have stale/wrong `Icon` paths in coachless's bundled data and 403 verbatim. Hardcoded in `lib/staticData.ts`'s `runeIconUrl` AND independently in `components/proAssets.ts` — these modules deliberately don't share code, so a third such rename needs updating in both. `IconWithFallback` is the generic safety net for any other icon 403/404.

**(f) Rune tooltip numbers come from CommunityDragon, not ddragon.** `components/runeDetail.ts` fetches CDragon's `perks.json`, client-cached with a 10-day TTL (no per-patch version to key off).

**(g) `purchaseOrder[].ts` (and prostage item-timeline `ts`) is SECONDS into the game, not milliseconds.**

**(h) prostage rows have structural gaps soloq rows don't** — `gameDurationSec` always `0`, `purchaseOrder`/`skillOrder` always `[]`. `role` can be `-1` (unresolved) and must never cause a row to be dropped.

**(i) Don't run two `next build`/`next dev` processes against one checkout** — an orphaned process locks `.next/trace`, `EPERM`s a subsequent build. Deleting an API route needs an extra sweep: clear the matching stale `.next/types/app/api/...` stub before re-running `tsc`, or `verify-fix.sh`'s tsc gate fails on a ghost type (hit in v0.51.2 removing `/api/pros/recent`).

**(j) `GET /api/pros` deliberately omits `allyPlayers`/`enemyPlayers`** from the list response (on-demand via `/api/pros/team-players` instead — a real 23.5kB/44.7kB payload cut). `cleanLeaguepediaName` strips wiki-disambiguation parentheticals at both ingest and read time.

**(k) `public/sw.js` carries a second, UNVERSIONED cache: `coachbuild-icons-v1`**, cache-first for `cdn.coachless.gg`. The `activate` handler's eviction sweep must keep excluding `ICON_CACHE` — a routine version bump must not wipe it.

**(l) `prostage_matches.game_id` is per-MATCH, not per-player** — any client state keyed on it must reset on a cross-player jump.

**(m) `IconWithFallback` is the single `<img>` sink for the whole app** — lazy-loading, explicit dimensions, 403/404 fallback glyph, on-device cache path. New icon call sites should always render through it.

**(n)/(p) `/history` and `/` (Builds) both integrate browser back/forward** via `NavHistoryState`/`useSheetBackNav` — every selection/sheet-open is a self-sufficient history entry. New modal/selection UI on either page must push/pop through the existing mechanism.

**(o) RESOLVED 2026-07-25 (v0.52.0) — pro-play ingest does NOT run on Vercel, by design now.** The old "untriaged gap" was two bugs stacked. (1) `resolveActiveTournaments` returns `[]` on a Cargo failure, which put the cursor out of range and made the route answer `{tournament:null, rowsSeen:0, errors:[], errorCount:0}` — an HTTP 200 indistinguishable from a healthy no-op, so weeks of dead ingest were invisible. That is now an explicit error. (2) The real blocker: **Leaguepedia is unreachable from Vercel by BOTH transports** — `api.php` returns "You've exceeded your rate limit" on the first call of a run (shared datacenter IPs), and `Special:CargoExport` returns **HTTP 403** (Cloudflare TLS/JA3 block). Both probed live against prod. **Pro-play therefore ingests from THIS MACHINE** via Scheduled Task `CoachBuildProstageIngest` (every 3h, `scripts/ingest-prostage-scheduled.ps1`, `--via-export` + curl transport) — same arrangement, same reason, as `CoachBuildDraftIngest`. Solo-queue (Riot API) is unaffected and still refreshes from Vercel. If pro games look stale, check the task and `%LOCALAPPDATA%\CoachBuild\prostage-ingest.log` first, NOT the Vercel cron.

**(u) Pro data freshness has THREE paths — know which one is failing before debugging.** (1) **Solo queue, on demand:** `POST /api/pros/refresh?proId=` fires when a player is opened (`ProHistoryResults`); active accounts only, 4 max, 10 matches each, 10-min cooldown. It is a POST because it mutates and spends the Riot key — as a GET it was cross-origin-triggerable by a bare `<img>` tag. Riot's API IS reachable from Vercel. (2) **Solo queue, background:** Scheduled Task `CoachBuildMatchIngest` (local, every 6h) — the Vercel cron is throughput-bound to ~5 accounts/2 days against **2801 accounts**, a ~3-year cycle, which is why 2440 accounts had never been fetched (measured 2026-07-25). (3) **Pro play:** Scheduled Task `CoachBuildProstageIngest` (local, every 3h) — Leaguepedia is Cloudflare-blocked from Vercel entirely, see gotcha (o). **A pro with no games is not automatically a bug:** check `pro_accounts.active` (retired/renamed smurfs are `false` — TheShy's only account is) and check Leaguepedia for whether they actually played.

**But do NOT conclude "they didn't play" from one source's silence.** This doc previously asserted "TheShy has NO 2026 pro games; IG's 2026 top laner is Breathe" — that was **WRONG**, and it is the single most expensive mistake made on this project. He played IG vs WBG in the LPL that same day; Leaguepedia simply had not been written yet. Absence in an editor-populated source is not evidence of absence, and the whole live-ingest path (`lib/prostage/liveIngest.ts`) exists because of it. Cross-check the source the user can actually see before stating a conclusion as fact.

**(q) Any component-owned `fetch` in a prop-keyed `useEffect` needs a stale-response guard** (`cancelled`-closure pattern) — a real bug class hit multiple times (`BuildTabContent.tsx` v0.27.1, a lane-flip race in v0.36.0 from a React stale-closure between two effects sharing `state`/`lane`). Any new component fetching off a prop-keyed effect must follow this from day one.

**(r) `public/sw.js`'s `install` handler doesn't call `self.skipWaiting()` unconditionally** — an update sits in `registration.waiting` until the user taps "Refresh" on the update toast. `ServiceWorkerRegister.tsx` gates the toast on `controller` being non-null (so first-ever install never shows it) and now persists dismissal in `localStorage` keyed to the waiting worker's `scriptURL` (v0.51.1 fix — the old `sessionStorage` boolean resurfaced the toast on every new tab/PWA relaunch).

**(s) A flat "top-N by frequency" aggregate must never be assumed positional.** Multiple real bugs (Pro Consensus rune-apply writing empty/wrong-slot pages, v0.48.3/0.48.4) came from treating a frequency-ranked list as if it preserved per-slot/per-row structure. Anything that needs slot-coherence (a full LCU rune page) must resolve per-ROW/per-SLOT modals explicitly (see `components/hextech/perkSlots.ts`), never derive it from a flat top-3.

**(t) A curated/frequency-based data-quality precedence must prefer the MORE SPECIFIC signal.** The `pro_role ?? role` vs `role ?? pro_role` bug (v0.49.1) — a roster-level attribute silently overrode a per-game one, corrupting team ordering. When merging two sources of the same fact at different granularity, the finer-grained one should generally win.

**(v) Every outbound `fetch` must go through `lib/fetchTimeout.ts`.** Before v0.58.0 not one hot path had a timeout, so a single hung socket burned the whole `maxDuration` (90s on patch-movers) instead of failing in ~4s. A bare `fetch(url)` in `lib/pro/**` or `lib/prostage/**` is now a bug, not a style choice.

**(w) The timeline claim is what stops `/api/prostage/timeline` being a free DDoS amplifier — don't "simplify" it.** The route atomically claims a game (`UPDATE ... WHERE timeline_status IS NULL AND (timeline_next_attempt_at IS NULL OR <= now()) ... RETURNING`) BEFORE any network call; a loser of that race gets 0 rows back (Postgres re-evaluates the predicate after the winner commits) and 429s having made zero outbound requests. On `transient` the same column moves out on exponential backoff (60s→1h). Two invariants: (1) the claim must stay BEFORE the walk, or the amplifier is back; (2) `timeline_status` must stay NULL on a transient result — `timeline_next_attempt_at` gates *when* a row may be retried, never *whether* it may be. Migration `0016`.

**(x) A classifier that tie-breaks on a bare count can be flipped by ONE data point.** `resolveDamageFamily` used `ap !== ad` and marked the result `confident: true` at a margin of 1 — so a single item (`2524` Bandlepipes, an incidental `AttackSpeed` tag) made Leona/Braum/Rell "AD" and suppressed the correct `Support`→AP class-tag fallback, which is how tank supports ended up shipping `Bruiser (AD)` lines. It now requires a margin of ≥2. This is a heuristic, not a proof: a second off-family-tagged support item would clear it. Confidence must be derived from the margin, never asserted beside it.

**(y) Curated item ids rot every patch, silently.** `3001` was labelled "Abyssal Mask" in two curated pools; in 16.13.1 `3001` is **Evenshroud** and Abyssal Mask is `8020`. `6691`/`3193` are unpurchasable. The tank pool ran at 6/8 with no signal. `curatedArchetypePool` now warns once per process on any curated id resolving to `purchasable: false` — but a WARN is belt-and-braces, not a guarantee; verify curated ids against the live catalog on every patch bump.

**(dd) An "independent second aggregation" is a second copy of a query, and it WILL miss the next fix.** v0.70.0 fixed the pro-play starvation in `ProConsensusCard` (`limit=200&proMin=100`) but `itemSetsApply.ts` performs its OWN `/api/pros` fetch for the LCU export — deliberately, see its header — and that copy silently kept `limit=100` with no floor. So the "Pro build" line the user got IN THEIR SHOP was still ~96% solo queue while the card directly beside it read 88 pro-play games. Fixed in v0.70.1, and pinned by a query-drift test in `components/__tests__/itemSetsApply.test.ts` that asserts the exact params. **When fixing a data-shaping bug, grep for every call site of that endpoint before calling it done** — the card is never the only consumer.

**(ee) The companion did NOT need changing for the third rune page — check the handler before assuming a contract change.** v0.70.0 shipped the OTP card read-only on the stated belief that a third LCU rune-page title required a `companion.ps1` change and therefore a user re-install. That was wrong, and it cost a follow-up ship. `Invoke-ApplyRunes` is title-AGNOSTIC beyond `Test-RunePayload`'s starts-with-`"CoachBuild"` gate: STEP 1 protects every page sharing the champ-scoped `replacePrefix`, STEP 2 matches its target by EXACT title, STEP 3 creates. So `pageSuffix:"OTP"` works against an already-installed companion. Item sets needed nothing either — the OTP line is a BLOCK inside the existing one-set-per-champion+role document, not a new set. The real consequence is SLOT PRESSURE (3 pages, 2 slots on a free account), which degrades correctly: a real click takes the manual branch and replaces the selected page (HARD RULE 5's consent carve-out), and AUTO mode still only ever writes the unsuffixed WPA page.

**(aa) A recency-sorted merge of two feeds with different CADENCE silently starves the slower one.** `GET /api/pros` fetched `limit` from each source, concatenated, sorted by `gameCreation` and sliced. Solo queue and pro play don't differ much in VOLUME — they differ in cadence (a pro queues most days; official matches happen on match days), so the newest N rows were essentially always solo queue. Measured live 2026-07-28 on Viktor mid: **94** fresh pro-play games in the DB, **4** in the 100-game Pro Consensus sample, because the 96th-newest soloq game was ~1 day newer than the newest pro-play game. Fixed by `lib/pro/mergeGames.ts`'s `proFloor` (reserve slots for the scarcer source, cap the floor by what exists, backfill when the other side is short) — opt-in via `proMin` so `/history`'s genuine "most recent games" feed is untouched. **Generalise the lesson before adding any third feed here:** ranking two differently-paced sources on one axis is a silent filter, not a merge.

**(bb) op.gg's leaderboard `puuid` is NOT a Riot puuid.** Live-probed 2026-07-28: every one returns `400 Bad Request - Exception decrypting <puuid>` from BOTH account-v1 and match-v5 — it is an op.gg-scoped identifier. `lib/otp/ingest.ts` therefore ignores it and re-resolves `game_name`+`tag_line` through account-v1, the same fallback `lib/pro/puuidResolve.ts` already does for lolpros accounts. Don't "optimise away" that extra call.

**(cc) OTP discovery runs LOCALLY; only the Riot half runs on Vercel.** Same split, same reason as gotcha (o): op.gg reachability from Vercel egress is UNVERIFIED and this repo has already lost weeks of ingest to assuming an external feed works from serverless. `/api/ingest/otp` is match-ingest ONLY (Riot is confirmed reachable, gotcha (u)); discovery runs from this machine via Scheduled Task `CoachBuildOtpIngest` (every 6h, `scripts/ingest-otp-scheduled.ps1`, log at `%LOCALAPPDATA%\CoachBuild\otp-ingest.log`) — its 6h schedule is offset 3h from `CoachBuildMatchIngest`'s, which is a real, still-accurate fact about THAT one pair.

**But schedule-offset stopped being the load-bearing mitigation once `CoachBuildOtpPriority` joined the same machine (Scheduled Task, hourly trigger, `scripts/ingest-otp-priority.ps1` → `scripts/ingest-otp-priority.mjs --max-hours 12`, deepens the featured one-trick fleet prioritized by the user's own played champions — see that script's own header for the full design).** This job has no free slot to be offset INTO: verified live 2026-07-31 against `%LOCALAPPDATA%\CoachBuild\otp-priority-host.log`, a run regularly rides its full 12-hour `--max-hours` ceiling (720 min observed twice), the hourly trigger relaunches it within about an hour of exit, and the result is a duty cycle of roughly 720/(720+60) ≈ **92% of wall-clock time** — there is no clock-based gap left to schedule anything else into. It is instead made safe by PREDICATE, not by timing: `lib/otp/riotYield.ts`'s `checkRiotJobsRunning` re-asks, before every unit of work, "is a process or Task-Scheduler-`Running` task matching `RIOT_JOB_MARKERS`/`RIOT_SCHEDULED_TASKS` (`CoachBuildMatchIngest`, `CoachBuildOtpIngest`) live right now?" — either signal saying busy means busy, and an enumeration failure also means busy (fail-closed). On a hit it parks at 30s polling and logs `YIELDING`/`still yielding`/`RESUMING`. **Confirmed working live the same day:** `otp-priority.log` shows a real `YIELDING — scheduled Riot job running: ... task CoachBuildOtpIngest` at 15:21 and `still yielding after 30.9 min` afterward — the predicate saw the collision and backed off exactly as designed. `lib/pro/pacer.ts` (gotcha (d)) still only serialises Riot calls WITHIN one process, so this predicate is what stops two Riot-calling processes ever running at once, not the 6h/3h offset above.

**(z) The companion's TLS bypass is scoped to loopback ONLY.** `Initialize-TlsShim`'s certificate callback inspects the sender's host; it exists solely for the League client's self-signed loopback endpoints. Everything else — including the `companion.version` check against `coachbuild.vercel.app` — gets real validation. Never widen this back to a blanket bypass. **NOT yet verified against a real self-signed LCU cert** (no League client in CI, and `-SelfTest`'s mock LCU is plain HTTP, so it cannot reach this path) — see `HANDOFF.md`.
