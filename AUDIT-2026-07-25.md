# AGENT 1 — PRO DATA PIPELINE

## P0-1 — The live/Leaguepedia supersede rule is INERT; the same pro game renders twice
**WARRANTED.** `app/api/pros/route.ts`, `lib/prostage/liveIngest.ts`, `lib/prostage/ingest.ts`,
`app/api/prostage/timeline/route.ts`, `migrations/0005_prostage_timeline.sql`

Both halves of the reconciliation hinge on `prostage_matches.lolesports_game_id` being set on the
**Leaguepedia** row:
- read path (all 3 prostage queries): `NOT (pm.game_id LIKE 'lolesports:%' AND EXISTS (… sup.lolesports_game_id = pm.lolesports_game_id AND sup.player_link = pm.player_link AND sup.game_id NOT LIKE 'lolesports:%'))`
- write path: `SELECT 1 … WHERE lolesports_game_id = ${game.id}` (the "skip if already held" check)

**`runProstageIngest`'s INSERT column list does NOT include `lolesports_game_id`.** Only two writers
ever set it: the on-demand `/api/prostage/timeline` compute path and
`scripts/backfill-prostage-timelines.mjs` (in no scheduled task). So a Leaguepedia row carries NULL
until a human opens that game's detail sheet. `NULL = NULL` is never true ⇒ live ingest writes a
duplicate row AND the read path shows both.

Concrete: LEC Summer games on 07-24 already had Leaguepedia rows on 07-25; the 07-25 live run used
`lookbackDays=3` so it covered them and wrote `lolesports:<id>` twins. Opening Caps returns both —
one card with items/runes, one with none — and because live rows store `ev.startTime` (MATCH start)
while Leaguepedia stores true per-game `DateTime_UTC`, **the two cards show different times**, so
they don't even look like duplicates.

Second independent break: `sup.player_link = pm.player_link` compares Leaguepedia's wiki page title
against the live feed's stripped summoner name. Leaguepedia links carry real-name disambiguators
(`"Zeka (Kim Geon-woo)"`); `stripTeamPrefix` yields `"Zeka"`. Supersede fails for every such player
even after a timeline resolve.

**Why my v0.55.0 sweep missed it:** "zero duplicate `(lolesports_game_id, player_link)` pairs" only
compares rows that BOTH have a non-null `lolesports_game_id` — precisely the population that
excludes every Leaguepedia twin. My sweep could not have detected this shape.

Knock-on: duplicates inflate `gamesTotal` in Pro Consensus (P1-2) and inflate the `limit`-capped
merge in `/api/pros`, pushing genuinely older games off the list.

Detection query: group `prostage_matches` by `(player_link, champion_id, date_trunc('day', game_datetime))`
having both a `game_id LIKE 'lolesports:%'` row and a non-`lolesports:` row.

Fix direction: make the Leaguepedia ingest establish the link, or match on `(player, champion, day)`
rather than a column only a lazy on-demand path populates. **A supersede rule keyed on a field the
superseding writer never writes is not a rule.** Fold in the cosmetic team CODE ("IG") vs NAME
("Invictus Gaming") mismatch as part of this fix — it only becomes visible once duplicates are gone.

## P1-1 — Scheduled prostage ingest still truncates at 500 Cargo rows (`paginate` is dead on that path)
**WARRANTED.** `scripts/ingest-prostage.mjs`, `lib/prostage/ingest.ts`, `scripts/ingest-prostage-scheduled.ps1`

`fetchScoreboardRows` paginates only when `opts.paginate` is true (default false). The ONLY caller
passing it is `scripts/ingest-prostage-seed.mjs`, a deletable one-off. The recurring production path
(3-hourly scheduled task → `ingest-prostage.mjs --via-export`) never passes it, nor does the route.
CLAUDE.md claims the ">500-row truncation risk is closed" — on the path that actually runs, it is not.

`LPL/2026 Season/Split 3` hits 500 rows at ~50 games. Query is `ORDER BY DateTime_UTC DESC LIMIT 500`,
so each run sees only the 50 newest games; Leaguepedia back-fills OUT OF ORDER (the entire premise of
the live-ingest feature), so a late-entered week-1 row sits below the cutoff forever. `rowsSeen` is
exactly 500 and nothing checks for that — **the same "cap hit looks identical to nothing-new"
signature v0.55.0 just fixed for `maxGames`, left unfixed one file over.**

## P1-2 — Pro Consensus item percentages understated by the share of itemless live rows
**WARRANTED.** `components/hextech/proConsensus.ts`, `lib/prostage/liveIngest.ts`

`gamesTotal = games.length`; every `ItemFrequency.share` is `count / gamesTotal`. Rune slots
deliberately get their own denominators ("so keystone-only prostage rows don't dilute the fraction");
items never did, because until v0.54.0 every prostage row carried Cargo `Items`. Live rows write
`final_items = '[]'`.

100 games, 15 live ⇒ an item in 40 of the 85 item-bearing games renders "40 (40%)" instead of 47%.
Every item/boots/starter row shifts down; the "From 100 pro games" denominator claims item coverage
it doesn't have. Keystone/spell aggregates ARE insulated — which makes the items row inconsistent
with its own neighbours on the same card. P0-1 duplicates compound it.
Fix: an `itemsSampleSize` counting games with non-empty `finalItems` (matches the existing pattern).

## P1-3 — A partially-written live game is permanently partial, and silent after run 1
**WARRANTED.** `lib/prostage/liveIngest.ts`

Each participant INSERT is its own statement inside a per-game `try`. Two paths leave <10 rows:
an unresolved champion `continue`s (exactly what `MonkeyKing` did), or a mid-loop throw (Neon
transient, statement timeout) after earlier participants committed. On the NEXT run the game matches
`SELECT 1 … WHERE lolesports_game_id = ${game.id} LIMIT 1` and is skipped — **it can never be
completed, and the run reports clean.** A 9-row game also fails `orderedSidesForGame`'s 5/5 gate, so
it silently loses its comp strip and Teams box for all 9 remaining players.
Fix: the existence check must be "do I hold ALL 10 rows", not "any".

## P1-1 — `/apply-runes` never validates `body.name` starts with "CoachBuild"

`$_.name -eq [string]$Body.name` then PUTs a full replacement to `/lol-perks/v1/pages/{id}`.

Not currently exploitable through the app's own code (all call sites go through
`components/hextech/runeApplyBody.ts` which hardcodes the `CoachBuild …` title) — needs XSS on the
origin plus the session token, or a future refactor. Defence-in-depth hole against a documented HARD

## P1-3 — `/api/prostage/timeline` is the worst unauthenticated cost amplifier
**WARRANTED.** `app/api/prostage/timeline/route.ts`, `lib/prostage/timeline.ts`, `lib/prostage/resolveGame.ts`

No auth, no cooldown, no rate limit. On `timeline_status IS NULL` it synchronously walks lolesports
schedule pages, then up to `WALK_MAX_POINTS=500` detail points at `WALK_CONCURRENCY=12` with
`WALK_RETRY_ATTEMPTS=2`, then ddragon — **≈750 outbound requests, NONE with a timeout** (bare
`fetch(url)` throughout). Then one UPDATE per player row.

Compounding: on `transient` it persists nothing (correct taint discipline) so **the next identical
request re-walks everything**. No negative cache, no attempt counter. `/api/pros` publicly returns
the `{id, playerLink}` pairs needed to drive it. Realistic non-adversarial trigger: a link-preview
crawler or aggressive reload during a lolesports blip.
Fix: `attempt_count`/`last_attempt_at` backoff column + `AbortSignal.timeout()` on walk fetches.

## P1-4 — `/api/pros/refresh` spends the Riot key from a **GET**; cooldown is per-pro not per-caller
**WARRANTED (verb change). SPECULATIVE (rate limiting).** `app/api/pros/refresh/route.ts`

The route is **well built** — UUID gate real and cheap-first, `active` filter correct, MAX_ACCOUNTS/
MATCHES_PER_ACCOUNT real bounds, and the cooldown genuinely engages (`ingestOneAccount` sets
`last_fetched_at` on success AND on the zero-rows/error path). Two gaps:
1. It's a **GET that mutates the DB and spends third-party budget** ⇒ triggerable cross-origin with
   no CORS involvement: `<img src="…/api/pros/refresh?proId=…">` fires for every visitor. POST would not.
2. **Cooldown is per-pro.** Rotating `proId` (enumerable via `/api/players?q=`) bypasses it entirely
   and walks the Riot key toward the cap — which per CLAUDE.md gotcha (d) **suspends the key** and
   blanks the whole Pro Players surface.
Cheap fix: switch to POST. Global rate limiting declined at this scale.

## P1-1 — Builds hero's WIN%/GAMES/CONFIDENCE always describe High-Elo, whatever elo tab is selected
**WARRANTED.** `components/hextech/ChampionHero.tsx`, `app/api/hero-stats/route.ts`,

Scenario: open Viktor MID, tap "Platinum". The build panel refetches on `[3]` and every rune/item
changes. The hero line one row above still reads the `[5,6,7]` numbers — per `lib/rankBrackets.ts`'s

directly beside a visibly-active "Platinum" pill. No on-screen correction exists:
`BuildResponse.tierLabel` renders only in `components/BuildCard.tsx`, which **nothing imports**
(see P2-4).

The confidence chip can also flip band: `confidenceBand` uses `HIGH_FLOOR = 15000` against the
un-bracketed count, so ~17k High-Elo / ~4.5k Diamond reads **HIGH CONFIDENCE** while the build shown
rests on a MEDIUM-band sample. That is exactly "claim HIGH CONFIDENCE on thin data".

Fix: accept `rank` on `/api/hero-stats`, thread into `FilterOpts.leagueTiers`, add `rankBracket` to
the `ChampionHero` effect deps and to `getHeroStats`' signature. **Keep the param OPTIONAL** —
`getMostPlayedLane` also calls `getHeroStats` and lane inference SHOULD stay un-bracketed (widest
sample).

## P2 (build engine)
- **P2-1 Patch Movers floors the current-patch sample but NOT the previous one, while ranking by
  absolute delta** (`lib/patchMovers.ts`). `computeMoverForChamp` checks `row.curr.games < minGames`

  `if (row.prev.games < minGames) return null;`
  (Separately: `MOVERS_MIN_GAMES = 1000` is thin for a DIFFERENCE of proportions — SE approx 2.2pp

- **P2-2 The archetype "(low data)" honesty threshold went stale when the line length changed**
  (`components/hextech/itemSetBody.ts`). `MIN_CATEGORY_MEASURED = 3` is justified by its own comment
